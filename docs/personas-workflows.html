Personas

🛠
AdLite Admin
Platform operator
admin
Goals
  • Onboard venues and advertisers
  • Configure devices and ad slots
  • Match advertisers to inventory
  • Monitor device and campaign health
Portal access
  • Full admin panel
  • Venues, advertisers, devices, slots, bookings
  • Impression reporting
🏪
Venue Manager
Business owner / location manager
venue
Goals
  • Earn passive revenue from existing screens
  • Minimal setup — plug in and done
  • See which screens are active
  • Track earnings over time
Portal access
  • Their devices and status
  • Revenue and impression summary
📣
Advertiser
Business or agency buying ad time
advertiser
Goals
  • Reach the right audience at the right place
  • Book specific time slots and locations
  • Upload and manage ad creatives
  • Verify ads are actually playing
Portal access
  • Their campaigns and bookings
  • Creative upload
  • Impression reports
📺
Kiosk Device
Android stick at venue — automated actor
device
Responsibilities
  • Register with API on first boot
  • Fetch and cache the ad playlist
  • Display creatives full-screen
  • Report heartbeat every minute
  • Report each impression after playback
Auth
  • Device JWT (non-expiring, RS256)
  • Rate-limited: 30 req/min

Workflows

1 Venue Onboarding Admin + Venue Manager + Device
  1. Admin → API
    Admin creates the venue record in the portal — name, category, address. API returns a venue ID.
  2. Venue Manager
    Venue manager receives the AdLite device (Android stick). Plugs it into the TV via HDMI and powers it via USB.
  3. Device → API
    Device boots, connects to WiFi, and calls POST /api/v1/devices/register with its hardware ID and venue ID. Receives a device JWT for all future requests.
  4. Admin → API
    Admin creates ad slots for the device — label, time window, days of week, duration, and price. Slots start in available status.
  5. Device
    Device begins its playback loop and heartbeat cycle. Shows a default screen until a booking goes active.
2 Advertiser Campaign Setup Admin + Advertiser
  1. Admin → API
    Admin creates an advertiser account — company name and email. Advertiser receives login credentials.
  2. Advertiser → API
    Advertiser uploads their ad creative via POST /api/v1/assets/upload. File is stored in Cloudflare R2 and a CDN URL is returned.
  3. Admin → API
    Admin creates a booking — linking the advertiser, slot, creative URL, date range, and price. Booking starts in pending status.
  4. API
    On the booking start date the status moves to active. The scheduler includes this creative in the device playlist. Redis cache expires within 60 seconds.
3 Ad Playback Loop Continuous — runs on every device
  1. Device → API
    Device requests its current playlist. API checks Redis first (playlist:{deviceID}, 60s TTL), falls back to Postgres on cache miss.
  2. Device
    Device displays each creative full-screen for its configured duration (15s or 30s), cycling through all active bookings in order.
  3. Device → API
    After each play, device calls POST /api/v1/devices/{id}/impression with the booking ID. API logs the impression for reporting.
  4. Device → API
    Every minute, device sends POST /api/v1/devices/{id}/heartbeat. API updates status = online and last_seen.
    Rate limited to 30 req/min per device across heartbeat + impression combined.
4 Booking Lifecycle Status transitions for a campaign
  1. Admin
    Booking created. Status: pending. Slot status moves to booked.
  2. API
    On starts_on date the booking becomes active. Scheduler begins including it in playlists.
  3. Advertiser
    Advertiser views impression counts in the portal throughout the campaign to verify delivery.
  4. API
    On ends_on date the booking moves to completed. The slot returns to available and can be sold again.
  5. Admin
    Admin can cancel a booking at any point, setting status to cancelled and freeing the slot immediately.
5 User Authentication & Session Admin, Venue Manager, Advertiser
  1. Admin / Venue / Advertiser → API
    User submits email + password to POST /api/v1/auth/login. API verifies bcrypt hash, issues an access token (15 min) and a refresh token (7 days).
  2. Portal
    Tokens stored in localStorage. Access token sent as Authorization: Bearer. Role decoded from JWT payload to show the correct nav and pages.
  3. Portal → API
    When the access token expires, the portal automatically calls POST /api/v1/auth/refresh. A new token pair is issued and the original request retries transparently.
  4. Admin / Venue / Advertiser
    On logout, tokens are cleared from localStorage and the refresh token is deleted server-side so it cannot be reused.
